## Gotchas and differences from the guide
1. **The tenant is not provisioned for the mini hack.** It has no *Workflows Mini Hack Template* workflow, no *Workflows Mini Hack HR Feed* source, and no reference identities (no Margaret Hamilton, Jean Bartik or anything at `navigate.example`). There are 21 workflows (all disabled), 12 sources and 4 identity profiles. So there is no template execution history to copy a payload from. We used the guide's fallback (build from the template JSON; the API create is the same as UI *Upload File*) and tested against existing identities.
2. **Cloudflare blocks Python's default User-Agent.** urllib got `HTTP 403 error code: 1010` while curl did not. `isc.py` sends its own UA.
3. **Internal step names.** The UI shows "Get New Hire" and "Get Manager", but the definition keys are `Get Identity` and `Get Identity 1`, and the JSONPath roots are `$.getIdentity` and `$.getIdentity1`. History events show this as `stepName` (lowerCamel of the key) next to `displayName`. Our email step key `Send Email` becomes `sendEmail`.
4. **`resultSelector` trims step output.** Get Manager only returns `attributes.displayName`, `attributes.email`, `displayName`, `emailAddress` and `id`. If you reference a field that isn't listed, the value is empty. The validator warns about this.
5. **`managerRef` vs `manager`.** The real v2 Get Identity output has `managerRef: {id, name}`, as the guide says. The library's `exampleOutput` shows `manager` instead, which is misleading. Use `managerRef.id`.
6. **The Send Email v2 body is an `htmlEditor` field.** Plain `\n` collapses in an HTML mail, so our JSON uses `<br/>`. (In the UI you can just type the lines.) `recipientEmailList` is a literal list, or `recipientEmailList.$` for a variable (CoLab workflows use this pattern). v1 used `recipientId.$`, and the API docs' create example still shows v1.
7. **Creating with `enabled:true` is rejected** by the API spec. Create disabled and then enable (step 4).
8. **Choice step shape** (taken from sailpoint-oss/colab-workflows, and confirmed working here): `{"type":"choice","choiceList":[{"comparator":"IsPresent","variableA.$":"$.getIdentity.managerRef.id","nextStep":"Get Identity 1"}],"defaultStep":"..."}`.
9. **Identity emails in this tenant are `@sailpointdemo.com` / `@sailpoint.com`**, not the guide's fictional `@navigate.example`. That makes the guide's "send it to the manager, nothing leaves the tenant" stretch goal unsafe here, so we did **not** create or test `identity-onboarding-to-manager`.

### Inconsistencies in the guide text (worth reporting to DevRel)
- Step 5 ("Fire the real event") says to upload the 9-row file to **Workflows Mini Hack HR Feed**, which is the shared reference source. That contradicts the warning not to touch shared objects. It should say *your* `<name> HR Feed`.
- In the Identity profile mappings table, **Department ← `lastname`** is almost certainly meant to be `department` (otherwise the email's department shows the surname). **Display Name ← `uid`** conflicts with step 5's "fullname becomes the identity's display name" (it should be `fullName`). With the table as written, the subject would say `robin.vance.x` and not `Robin Vance`.
- Numbering: there are two sections numbered "3."; Part 1 has sub-steps 1–6, but the "You will create" table cites Steps 1/4/6; and the docs list says "steps 3 and 10".
- "Upload the whole file to Admin → Connections → Sources …" uses the path *Account Aggregation*, while Part 1 uses *Account Management → Account Aggregation → Import Accounts*.

## UI steps left for you
Every one of these creates or changes objects in the shared tenant, so they were left for you (with UI admin credentials) or for an explicit go-ahead.
1. **Source:** Admin → Connections → Sources → Create New → *Delimited File* → Configure. Name `Shane Cotta HR Feed`, Owner `hack.day`, Platform Type Saas → Continue.
2. **Schema:** Your source → Account Management → Account Schema → Upload Schema → `guide-files/workflows-hack-day-schema.csv`. Set Account ID and Account Name to `uid`.
3. **Manager correlation:** Account Management → Account Correlation → Manager Correlation: Identity Attribute `Name`, Account Attribute `managerUid` → Save.
4. **Aggregate:** Account Management → Account Aggregation → Import Accounts → drop `guide-files/hr-feed.csv` (8 rows).
5. **Identity profile:** Admin → Identity Management → Identity Profiles → Create New. Name `Shane Cotta HR Feed`, source = yours. On the Mappings tab: uid←uid, Work Email←email, Family Name←lastname, Given Name←firstname, Department←**department**, Display Name←**fullName**, Job Title←jobTitle, Manager←managerUid. Then Save and Apply Changes. Check that your Margaret Hamilton has Manager = a link to jean.bartik.
6. **Recipient:** Admin → Workflows → *Shane Cotta Identity Onboarding* → Edit in Builder → *Send Onboarding Email* → Recipient Email Addresses = your inbox → Save. (Or use `build_workflow.py --recipient …` and then `isc.py update …`.) Optionally use Test Workflow with the id of your new Margaret Hamilton.
7. **Enable:** set the workflow to Enabled (or run `python3 scripts/isc.py enable workflow/identity-onboarding.workflow.json`). This is a shared tenant, so consider adding a trigger filter first, for example `$.attributes[?(@.displayName =~ /.*shanecotta.*/)]`, which follows the guide's "Filter at the trigger" stretch goal. Test that filter, because the payload's `displayName` is the uid at creation time.
8. **Fire:** Your source → Account Aggregation → Import Accounts → `data/hr-feed-with-new-hire.csv` (all 9 rows). Watch Admin → Identities for Robin Vance, then the workflow's Executions, then your inbox.
9. **Clean-up afterwards (optional):** disable the workflow so it stops reacting to other people's joiners.
